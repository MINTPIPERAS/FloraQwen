## 2. 数据集拉取：Oxford 102 Flowers

### 2.1 做了什么

1. 用项目自带脚本 `scripts/download_flowers102.py` 从牛津大学 VGG 服务器拉取：
   - `102flowers.tgz`（官方 Content-Length 345MB，解压 8189 张 jpg）
   - `imagelabels.mat`（每张图的类别标签 1–102）
   - `setid.mat`（官方 train/val/test 划分：1020/1020/6149）
2. 产出 `data/raw/flowers102/`：`images/`（8189 张）、`labels.csv`、`splits.json`、`by_class/`（按类别硬链接整理，零额外磁盘占用）。
3. 抓取官方类别页 `categories.html`，获得 102 个物种英文名的权威顺序（与 `imagelabels.mat` 的 1–102 编号一一对应）。

### 2.2 为什么选它

- 是计算机视觉细粒度分类的经典国际基线（Nilsback & Zisserman, 2008），有官方划分，可直接支撑 M3/M4（微调 + 评估）；
- 脚本在项目里已备好（`download_flowers102.py`），走官方源最可靠（无第三方转存损坏风险）；
- 8189 张对 8GB 显卡的 QLoRA 是合适的规模。

### 2.3 遇到的坑与修复

1. **解压目录结构与脚本假设不符**：tgz 内是 `jpg/` 子目录而不是裸 jpg 文件，脚本 `glob("*.jpg")` 搬空后 `rmdir` 失败（WinError 145）。修复：改 `rglob("*.jpg")` + `shutil.rmtree(ignore_errors=True)`（见 `download_flowers102.py`）。
2. **牛津服务器 301 重定向**：`robots.ox.ac.uk` → `thor.robots.ox.ac.uk`，urllib 自动跟随，无需处理，但速度仅 ~3MB/min，全量下载约 80 分钟（后台跑完，无人工干预）。

## 3. 数据管道：从 102 个英文类别到中文问答训练集

### 3.1 做了什么

新增 `scripts/make_flowers102_labels.py`：

- 102 个官方英文名 → 中文名 + 科 + 科级形态特征（全部手写映射，逐条有分类学依据）；
- 少数无法可靠定科的园艺品种（`bolero deep blue`、`cape flower`）标注为"园艺栽培品种"，并在脚本 `SRC_NOTES` 里逐条说明置信度；
- 只取官方 train 划分（1020 张，每类 10 张）生成 `data/raw/labels.csv`（保留 val/test 供后续评估，避免数据泄漏）。

然后用 `prepare_data.py`（项目既有管道）生成 `data/processed/train.json`：**3081 条 ShareGPT 样本**（每张图随机 2–4 种提问变体 × 4 种回答模板），覆盖全部 102 类。旧占位数据备份为 `train.example.json.bak`，模板保留在 `labels.example.csv`。

### 3.2 为什么这样做

- 本项目的训练格式是 **VQA（视觉问答）而不是分类头**：Flowers102 只有数字标签，必须映射成"这是 XX（学名、科属）"的自然语言回答才有训练价值；
- 中文名/科属/特征全部采用**科级**通用描述（如"头状花序，具舌状花与管状花"），而不是逐种编造细节——宁可保守也不注入幻觉性事实；
- 用官方 train 划分训练、留 test 评估，是防止"背答案"式虚高指标的底线操作。

### 3.3 原理（一句话）

ShareGPT 格式（`conversations + images`）是当前视觉语言模型微调的事实标准，`prepare_data.py` 通过问题/回答模板把单标签扩展成多轮换问法，等效于低成本数据增强，提升模型对同一物种不同问法的泛化。

## 4. 模型加载段错误：诊断、原理与修复（本日核心攻坚）

### 4.1 现象

`AutoModelForImageTextToText.from_pretrained("Qwen/Qwen3-VL-4B-Instruct", quantization_config=4bit, device_map="auto")` 在 Windows + CUDA 下**每次都在加载进度 216/713 张量处（约 30%）进程直接段错误退出**（EXIT=139，无 Python traceback）。

### 4.2 诊断过程（做了什么、为什么）

| 步骤 | 实验 | 结果 | 排除/确认 |
|---|---|---|---|
| 1 | faulthandler 抓崩溃栈 | 崩溃点在 `torch.storage.__getitem__` ← transformers `_materialize_copy` 的 `tensor[...]` 切片 | 崩溃在"从 safetensors 切片读数据"，不在量化、不在 GPU 内核 |
| 2 | 最小复现（单独读 216 号张量并量化） | 通过 | 单张量读写与 bnb 量化本身没问题 |
| 3 | 隔离测试（按加载顺序裸读整个分片） | 通过 | safetensors/torch 读取层本身没问题 |
| 4 | 变体对照（换 device_map / dtype / 双量化 / low_cpu_mem_usage） | 全部在同一位置崩溃 | 与这些参数无关 |
| 5 | **CPU 加载对照**（`device_map="cpu"`） | **713/713 全部加载成功（23s）** | 崩溃只在 CUDA 路径出现 → 指向 Windows 内存提交与 mmap 的交互 |
| 6 | 查页文件/内存 | 15.6GB RAM 剩 5.3GB，页文件 17.7GB 已用 10.9GB | 系统提交空间紧张 |
| 7 | 检索上游 issue | HF transformers **#48285**：`from_pretrained` 在 Windows 上对多分片大模型崩溃，根因确认 | 与本机症状逐条吻合 |

### 4.3 根因原理

transformers v5 的加载引擎用 `safe_open(..., backend="mmap")` **同时打开所有 safetensors 分片并保持到加载结束**（本机 2 个分片共 8.9GB）：

- Linux 上 COW（写时复制）mmap 几乎不占内存（内核 overcommit，页只在写入时分配）；
- **Windows 上每页 COW 映射在 map 时就要按提交限额（commit limit = RAM + 页文件）全额记账**；
- 于是 8.9GB 的映射 + CUDA 上下文/暂存 + 进程本身把提交空间吃穿，随加载推进页逐渐缺页调入，到 ~30% 处提交耗尽，下一次页缺页直接访问违规（0xC0000005），进程无痕死亡；
- 崩溃点恒定在 216/713 是因为加载路径完全确定性（每次内存布局一致）。

这也解释了 2026-08-18 报告里的"已修复"为何今天复现不了：当时的验证很可能在无 CUDA 的沙箱里完成（本日实验 5 证明 CPU 路径本来就不崩溃），且当时的内存/页文件状态与今天不同。

### 4.4 修复

按上游 **PR huggingface/transformers#48341**（issue #48285 的官方修复）给本机 transformers 5.5.0 打最小补丁（`site-packages/transformers/modeling_utils.py` 一处）：Windows 上把 safetensors 打开后端从 `mmap` 换成 **`pread`**（按需读切片、不建立 COW 映射、无提交记账）。修复后冒烟测试通过：**713/713 加载成功，峰值显存 2.73GB**。

> 长期方案：升级 transformers 到包含该修复的版本（>5.5.0，PR 合入 main）。本次选择就地补丁是为了不动其余依赖版本（项目锁定组合已实测可用）。

### 4.5 顺带发现并修正的训练脚本问题（`scripts/train_lora_trl.py`）

1. **视觉输入根本没进模型**：原 `build_dataset` 把 `<image>` 标记从文本里删掉，而 Qwen3-VL 的 chat template 只有在消息含 `{"type": "image"}` 内容块时才渲染视觉占位符——原写法训练出来的是"盲人模型"。已改为图像内容块形式（与 `infer.py` 一致）。
2. **标签掩码错位**：原 collator 用纯文本 tokenize 计算 prompt 长度，而实际 input_ids 里图像 token 会展开成数百个 token，导致掩码错位。已改为"带图重处理 prompt 文本"取真实长度，并用 attention_mask 掩掉 padding。

新增 `logs/collator_test.py` 验证：视觉 token 确实进入 input_ids，回答部分 46–49 token 参与 loss，prompt 正确掩码。✅

## 5. 训练启动

### 5.1 配置（configs/lora_config.yaml）

| 项 | 值 | 说明 |
|---|---|---|
| 基座 | Qwen/Qwen3-VL-4B-Instruct | 4-bit NF4 + 双量化 |
| 方法 | QLoRA | r=16, alpha=32, dropout=0.05，目标模块为 7 类线性层（含 gate/up/down） |
| 视觉编码器 | **冻结** | 花草识别不需要微调视觉塔，且省显存 |
| batch / 累积 | 1 / 16 | 等效 batch 16，显存不变 |
| 步数 | 579（3 epoch × 193） | 3081 样本 ÷ 16 |
| 学习率 | 1e-4，cosine，warmup 3% | QLoRA 常规起点 |
| 精度 | bf16 | RTX 4060 支持，比 fp16 稳 |
| 梯度检查点 | 开（非重入） | 省显存关键项 |
| 输出 | models/lora-qwen3vl-4b-flora | 保存 LoRA adapter |

### 5.2 状态

- ✅ 模型 4-bit 加载成功；LoRA 注入成功；数据全部载入
- ✅ 训练进入主循环，GPU 99% 满载、显存 7.0GB
- ⚠️ 日志中 `checkpoint` 相关 UserWarning 均为 torch 2.11 的弃用提示，无害

### 5.3 试运行决策：全量 → 子集

- 首轮按全量 3081 条启动后实测单步 **31s**（batch=1×16 累积，短序列 ~411 token，主要受 Windows 下 bitsandbytes 4-bit 无融合内核影响），579 步 ≈ **5 小时**——超出"尝试训练"的合理时长；
- 改为**试运行子集**：每类 3 张（`prepare_data.py --max-per-class 3`）→ 915 条样本 → 174 步 ≈ **90 分钟**，仍覆盖全部 102 类，足以验证管道、观察 loss 下降并产出可加载的 adapter；
- 全量数据备份为 `data/processed/train.full.json`，可随时换回跑 v2（建议夜间/闲时）。

### 5.4 评估集构建（为 M4 预置）

新增 `scripts/build_test_set.py`：从官方 test 划分（6149 张）按中文名目录硬链接构建 `data/test/<中文名>/`（零额外磁盘）。本次每类取 20 张共 **2040 张**；评估时用 `evaluate.py --limit N` 控制时长。

## 9. 追加：标签映射顺序 bug 的发现与修正（18:50 后）

### 9.1 现象

带 adapter 推理一张官方标签为 54 的测试图（当时在 `data/test/荷花/` 目录下）：微调模型回答"沙漠玫瑰"，基座模型却描述"黄色舌状花瓣……符合向日葵特征"。三方矛盾 → 追查数据本身。

### 9.2 根因

- `imagelabels.mat` 的类别编号 1–102 对应的是**官方原始类别顺序**；
- 而我在 §2 中从 VGG 官网 `categories.html` 抓取的列表是**按字母排序**的——直接按页面序号映射标签编号，导致 **102 个类全部错位**（如标签 54 实际是 sunflower，被映射成了"荷花"）；
- 权威顺序以 TensorFlow Datasets 的 `oxford_flowers102` builder 类名列表为准（逐条核对后照录进 `make_flowers102_labels.py` 的 `CANONICAL_NAMES`）。

### 9.3 验证与修复

- 颜色分析佐证：标签 54 的图黄色占比 47%（向日葵特征），与基座模型判断一致；
- 修复：重写 `make_flowers102_labels.py`（英文名→中文/科/特征的映射数据不变，只改编号键位），并重新生成 `labels.csv`（train 1020 行）、`labels.all.csv`（8189 行）、`train.json`（915 条子集）、`train.full.json`（24466 条）、`data/test/`（2040 张）；
- ⚠️ **已训练出的 `models/lora-qwen3vl-4b-flora` 是错误标签的产物，需重训后才能用于推理**（重训命令与时长见训练操作指南）。

### 9.4 教训

从任何网站页面抓取"编号 ↔ 名称"对应关系时，必须先验证页面的排序方式与数据集的标签编号定义是否一致；可用一张已知标签图片的视觉特征（颜色/形态）做交叉验证，或直接以数据集官方 builder 代码为唯一权威来源。
