## 4. 模型拉取失败根因与思路评估

### 4.1 事实证据链

1. F 盘 Qwen 缓存内**只有 11MB 元数据**（config/tokenizer 等），两个 safetensors 大分片（4.97GB + 3.91GB，合计 8.9GB）**从未成功落地**，且当前无任何 `.dl` 断点文件残留；
2. 尝试时间线：8/14 `snapshot_download`（`.locks` 痕迹 18:53）→ 8/14 20:11 `.no_exist` 记录（404）→ 8/18 17:37 最后一次 curl 下载（blobs 目录 mtime），仍失败；
3. `logs/download_single.ps1` v3（8/18 17:39 最新一版）的逻辑是：断点续传 → 大小校验 → sha256 校验 → **失败即删除重下，12 轮循环**——说明此前多次出现"大小不符 / sha256 不符"；
4. 方案文档 §3.3 已自述：hf-mirror 大文件速度 0.3~4.5MB/s、AWS CDN 对并发连接限流（多连接 0 字节）、必须禁用 Xet 否则 401。

### 4.2 根因判断

- **主因**：hf-mirror 的大文件经 **AWS CDN 签名 URL** 重定向。签名 URL 有时效（通常 15min~2h），而 4.9GB 分片按 0.3~4.5MB/s 需 30min~4h——**下载中途 URL 过期 → 断点续传失效/内容截断 → 大小或 sha256 校验失败**。手搓 curl 脚本无法解决这个问题，只能"删了重下"，在限流下反复失败；
- **次因**：Xet 401 陷阱——任何未设 `HF_HUB_DISABLE_XET=1` 的 huggingface_hub 尝试都会直接失败（README 已记录此坑）；
- 注：本次核查运行在受限沙箱内，无法实测外网连通性；上述结论基于缓存痕迹 + 方案文档自述，最终网络验证请在你的终端执行。

### 4.3 思路评估：项目路线没问题，下载通道选错了

**项目技术路线（Qwen3-VL-4B + QLoRA，8GB 显存）是正确的、文档化的、脚本化的**，问题只出在"获取模型的方式"上——用 hf-mirror + 手搓 curl 脚本啃 8.9GB 大文件，是国内网络下最脆弱的组合。

**建议改走以下通道（按优先级）**：

1. **ModelScope（魔搭，阿里官方，国内直连）** —— Qwen 系模型官方托管，多线程 + 断点续传 + 校验，最可靠：
   ```powershell
   pip install modelscope -i https://pypi.tuna.tsinghua.edu.cn/simple
   modelscope download --model Qwen/Qwen3-VL-4B-Instruct --local_dir F:\hf-cache\models\Qwen3-VL-4B-Instruct
   ```
   之后 `infer.py` / `train_lora.py` 把模型名换成该本地目录即可（transformers 直接加载本地路径），不再依赖 HF。
2. **huggingface_hub 官方 CLI**（若坚持走 HF）——自带断点续传、指数退避重试、etag 校验，比手搓 curl 可靠得多：
   ```powershell
   $env:HF_ENDPOINT="https://hf-mirror.com"; $env:HF_HUB_DISABLE_XET="1"
   hf download Qwen/Qwen3-VL-4B-Instruct --local-dir F:\hf-cache\models\Qwen3-VL-4B-Instruct
   ```
3. **Ollama GGUF**（一石二鸟：M6 部署本来就要 GGUF/Ollama）——`ollama pull qwen3-vl:4b`；GGUF 也可从 ModelScope 下载后本地 `ollama create`。
4. 若带宽长期受限：先用 **Qwen3-VL-2B（2.3GB）** 跑通全流程，再换 4B。

## 6. 补充：infer.py 加载崩溃根因与修复（同日 21:xx 发现）

### 现象
`infer.py` 4-bit 加载基座时，**每次都在 ~30%（约 216/713 张量）处进程静默消失**（无 Python 报错），Windows 事件日志记录：`python.exe` / `torch_cpu.dll` / **异常代码 0xc0000005**（访问冲突），偏移量两次完全相同（0x6655d19）→ 确定性原生崩溃。

### 排查过程
1. 事件日志确认崩溃签名；检查非模型问题（权重已 sha256 校验、缓存离线验证完整）；
2. 沙箱内完整复现：`from_pretrained(device_map="auto", dtype=torch.bfloat16, quantization_config=4bit)` → 同样在 31% 崩溃（EXIT=-1073741819）；
3. **变体对照测试**（9 组参数组合，逐一实测）：
   - ❌ 崩溃：`dtype=bf16`+4bit（原始配置）、8-bit 量化
   - ✅ 成功：**不传 dtype**、`dtype=fp16`、`low_cpu_mem_usage=True`、`device_map="cuda:0"`、去掉双量化、纯 bf16 CPU

### 根因与修复
- **根因**：transformers 5.5.0 + bitsandbytes 4-bit 加载时传 `dtype=torch.bfloat16`，在 Windows 上触发 torch_cpu.dll 的 CPU 侧类型转换路径原生崩溃；
- **修复**：`scripts/infer.py` 与 `scripts/train_lora_trl.py` **去掉 dtype/torch_dtype 参数**（4-bit 走 fp16 路径），同时补了 UTF-8 输出（模型回答含 emoji 时 GBK 控制台会打印失败）；
- **验证**：修复后 713/713 权重完整加载（~17s），`rose_001.jpg` 推理成功（80.5s，输出完整中文分析），事件日志无新崩溃。

### 教训（写给自己）
Windows + transformers 5.x 加载量化模型时：**量化加载不要传 dtype/torch_dtype**；原生崩溃（无 traceback）查 Windows 事件日志（`Get-WinEvent -LogName Application`）确认故障模块与异常码。
